1. Goal and definition of done

After phase 6 a person who knows their role but not WCAG has a place to start: an ordered set of lessons that walks them through the criteria that matter for their work, with a short quiz after each lesson to check they got it. It is the "by learning path" entry point from section 4 of the main plan.

Done when:

  • Five paths are in the app: developer, designer, content author, tester, and the legal minimum for a public body. Every lesson has a quiz.
  • A path can be completed end to end from the keyboard: open it, go through every lesson with "next", answer each quiz, mark each lesson done, and see the path as complete. A Playwright test does exactly this.
  • Progress survives a reload and is visible on /sciezki and on the path page. With storage blocked, everything still works for the length of the visit.
  • Every lesson, quiz and link between them is checked by the content tests, the same way criteria, examples and provisions are.

3. Progress without accounts

One localStorage key, a11y-playground/postep, holding a versioned JSON object. Its shape copies the progress and quizAttempts tables from section 9 of the main plan, minus userId, so phase 5 can import it on first sign-in without a translation layer.

// src/progress/store.ts
const Progress = type({
  v: "1",
  lessons: { "[string]": { status: "'ukonczona'", updatedAt: IsoDateTime } },
  quizzes: { "[string]": { answers: "Record<string, string[]>", score: "number", total: "number", completedAt: IsoDateTime } },
});
// keys are LessonKey: `${PathSlug}/${LessonSlug}`, e.g. "programista/klawiatura-i-fokus"
  • One lesson state. A lesson is done or not. The reader marks it with a toggle button. Finishing the quiz does not mark the lesson, and an unanswered quiz does not block it: paths are ungated, as the main plan says.
  • Last attempt only. A new attempt replaces the old one. History is phase 5's problem if anyone asks for it.
  • Read through useSyncExternalStore. The server snapshot is empty progress, so prerendered HTML never claims anything and hydration does not mismatch. Subscribing to the storage event keeps two open tabs in sync for free.
  • Untrusted input. What comes out of storage is validated with ArkType. Anything invalid, from an old version or a hand edit, is dropped and replaced with empty progress. Keys that no longer match a lesson are ignored, not deleted, so renaming a lesson loses its state but nothing crashes.
  • Storage blocked. Reads and writes are wrapped. If storage throws, progress lives in memory for the visit and the line under the list says so.
  • Privacy. Nothing leaves the browser. /sciezki says "Postęp zapisuje się tylko w tej przeglądarce" next to a "Wyczyść postęp" button. No cookie banner: this is storage the reader asks for, not tracking.

4. Content format

Same pattern as the examples: one folder per path, Markdown with ArkType-validated frontmatter, parsed server-side at build time.

content/sciezki/programista/
  index.md                     # the path
  klawiatura-i-fokus.md        # a lesson
  klawiatura-i-fokus.quiz.yaml # its quiz
# index.md
---
title: Programista
role: programista            # a Role from sections.ts; absent on minimum-prawne
summary: Jak pisać kod, który działa z klawiaturą i czytnikiem ekranu…
lessons: [semantyka-najpierw, nazwy-dostepne, klawiatura-i-fokus, …]
status: szkic
---
Intro paragraph shown on the path page.
# klawiatura-i-fokus.md
---
title: Klawiatura i fokus
summary: Każda akcja z klawiatury, widoczny fokus i okno modalne…
criteria: ["2.1.1", "2.1.2", "2.4.3", "2.4.7", "2.4.11"]
examples: [okno-modalne-i-fokus, kontrast-stanow]
law: []                      # LegalUnitIds, used by the legal path
keep:                        # "Zapamiętaj", 2 to 4 lines
  - Wszystko, co działa myszą, działa klawiaturą.
  - …
status: szkic
---
Lesson body in Markdown, with slownik: and prawo: links like everywhere else.
# klawiatura-i-fokus.quiz.yaml
- id: div-jako-przycisk
  prompt: Które kryterium łamie ten kod?
  code: '<div class="btn" onclick="zapisz()">Zapisz</div>'
  options:
    - { criterion: "2.1.1", correct: true, why: Div nie dostaje fokusu… }
    - { criterion: "1.4.3", why: W kodzie nie ma kolorów… }
- id: okno-modalne
  prompt: Okno modalne jest otwarte. Co powinno działać?
  options:
    - { text: Fokus przechodzi do okna, correct: true, why: … }
    - { text: Tab może wyjść na stronę pod oknem, why: … }
  • Two question kinds, derived, not declared. One correct option renders radios, more than one renders checkboxes with "Zaznacz wszystkie poprawne". Code and "point out the fault" are the same kind with a code field or element names as options. Fewer knobs, same four question types.
  • An option is text or a criterion. criterion renders the number and Polish name from the registry and links to it after checking, so a quiz cannot name a criterion wrong.
  • Every option has why. The main plan asks for an explanation on every answer, correct ones included.
  • Types. Path and lesson slugs come from Markdown, so like criterion content they are strings checked by tests, not a union checked by tsc. criteria, examples and law are narrowed to CriterionId, example slugs and LegalUnitId by the parser, which fails the build on an unknown id.

6. Quiz behaviour

  • Markup. One fieldset per question, the prompt as legend, native radios or checkboxes with 44-pixel labels. Code snippets are a focusable, labelled pre, so a long line can be scrolled from the keyboard.
  • Feedback. After checking, every option shows "Poprawna", "Niepoprawna" or "Pominięta, a poprawna" with a glyph and its why. Colour only repeats what the word says. Once checked, a question's inputs are disabled; "Rozwiąż jeszcze raz" in the summary starts the whole quiz over.
  • Announcement. The verdict of each checked question goes to a polite live region; focus stays on the button the reader pressed.
  • Scoring. A question counts as right only when the selection matches exactly. The score is "2 z 3", nothing more.
  • One question at a time (variant 4C). The quiz shows one question, with "Pytanie 2 z 3" in its legend and a decorative step bar. "Sprawdź" shows the feedback and turns into "Następne pytanie". That button moves focus to the next question's legend (tabindex="-1"), the one place the quiz moves focus. There is no going back or skipping ahead. After the last question comes a summary: the score, one line per question with its verdict, "Rozwiąż jeszcze raz". The attempt is stored when the summary appears.
  • Without JavaScript. The prerendered page shows the first question without the check button. The lesson itself is fully readable; the quiz needs JS, like the filters on /kryteria.

7. Pages

  • /sciezki: the five paths, lesson counts, progress where there is some, "continue" to the first unfinished lesson, the storage note and "Wyczyść postęp". Replaces the placeholder. Screen 1 in the mocks.
  • /sciezki/$path: intro, the lessons in order with status and quiz score, "continue". Screen 2.
  • /sciezki/$path/$lesson: the lesson, "Zapamiętaj", the material it points at (criteria, examples, provisions), the quiz, the done toggle, previous and next. Screen 3. Route changes already announce the new heading, so moving between lessons needs nothing new.
  • Criterion page: a "W ścieżkach" line next to the examples, linking to the lessons that list the criterion.
  • Search: lessons join the index with title, summary and body, as a fifth group, "Ścieżki".
  • Prerendering: every path and lesson page is prerendered. Progress and the quiz hydrate on top.

8. Tests

  • Content (Vitest): every path parses; its lessons list and the lesson files match one to one; every criterion, example and provision id resolves; every lesson has a quiz with 3 to 5 questions; every question has at least one correct option and every option a why; question ids are unique within a quiz; drafts carry no lastVerified, verified files are at most 12 months old.
  • Progress (Vitest): the store round-trips, rejects a malformed or older-version value without throwing, and falls back to memory when storage throws. Scoring on a handful of single and multiple choice cases.
  • End to end (Playwright): the definition of done, keyboard only: /sciezki → the developer path → every lesson through "next", one quiz answered question by question to its summary, each lesson marked done → the path shows 7 of 7. Reload, and the state is still there.
  • Axe: /sciezki, one path page, one lesson with its quiz on the first question, after checking it, and on the summary.
