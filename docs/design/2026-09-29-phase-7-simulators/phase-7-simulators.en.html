Plan: phase 7, impairment simulators

Detailed plan for phase 7 of the main plan, section 8.2. Mocks of the picker, /symulatory and each simulator's output: simulators-mocks.html. Plan version: 2026-09-29.

The examples run in iframes with an opaque origin (sandbox="allow-scripts", no allow-same-origin). The page cannot read or style what is inside. Every simulator below either asks the frame over postMessage, resizes the frame from outside, or is computed at build time. The sandbox stays as it is.

Changes after work started

Decisions made while building phase 7. Where they conflict with the sections below, these win.

  • The screen reader list comes from a Vite plugin (section 5). jsdom cannot run from the bundled server: it reads its own files next to its code. So src/content/reading-order.vite.ts computes every list in Node while Vite builds and serves the result as virtual:reading-order. jsdom and dom-accessibility-api are dev dependencies and nothing of them ships.
  • Fragment scripts run. jsdom runs each fragment's own script before the walk, so a list the script fills in (the reorder example) is read. The fragments are our content, not user input.
  • Unknown roles fail a test, not tsc (section 5). getRole returns a plain string, so the compiler cannot check the Polish role map. The reading order test runs every example and expects no role without a Polish name.
  • The narrow frame scrolls inside itself (section 8). At 320 pixels the overflow is in the iframe's own document, so there is no extra scrollable region around it. The verdict under the frame carries the information.
  • The sandbox gains allow-forms (section 12). Without it the browser drops a form submission before the submit event, so the form example never showed its error, which the colour notes ask the reader to trigger. The origin stays opaque.
  • The new example is "2 minuty", not "1 token" (section 6). The fix changes two properties per element, not a design token.

1. Goal and definition of done

After phase 7 a reader can look at any example through someone else's constraints: without colour, with blurred sight, without a mouse, through a screen reader, on a narrow screen. The broken and the fixed variant go through the same simulator, so the reader sees why the fix matters, not only that it exists.

Done when:

  • All five simulators from section 8.2 of the main plan work on every example page.
  • No simulator is the only carrier of information. Each one puts text next to the frames: a description of what changed, a list of Tab stops, a list of announcements, or a measured verdict.
  • No simulator is on by default. The choice lives in ?symulacja=, so a simulated view can be shared as a link and survives a reload.
  • The picker and every simulator can be used from the keyboard. A Playwright test does this.
  • /symulatory says what each simulator shows and what it does not, and links into the examples where it teaches most.

4. How the page talks to the frame

The demo document already posts its height to the page and answers "a11y-example-measure". Phase 7 widens that one channel instead of adding a second.

  • Page to frame: { a11ySimulation: SimulationId | null }. The frame sets data-symulacja on its <html>, and the filters, the text size and the keyboard mode hang off that attribute in the demo's base styles and script. The page sends the message when the choice changes and again whenever the frame reports in, so a reloaded or late-started frame (the motion examples) picks up the current mode.
  • Frame to page: the height report gains width (the document's scrollWidth), which gives the 320-pixel verdict for free. Keyboard mode adds { a11yFocusStep: { n, name, role } } and { a11yBlockedClick: true }. The page checks every message with ArkType and matches it to its frame by event.source, as it does today.
  • Filters live inside the frame. The SVG filter definitions go into the demo document, so nothing depends on how a browser applies a parent's url() filter to an iframe.
  • Blocking the mouse, not the keyboard. In keyboard mode the frame cancels pointerdown, and cancels click only when event.detail > 0. Enter and Space on a button fire a click with detail === 0, so they still work. A blocked click shows a notice inside the frame and tells the page, which updates the count and announces it once in a polite live region.
  • Focus trace. On every focusin the frame draws a numbered badge next to the element and posts the step. The step's name is a short in-frame approximation: aria-label, then aria-labelledby, then an associated label, then the text. The page renders the steps as an ordered list under the frame. The list is not a live region: announcing every Tab would talk over the reader's own screen reader.
  • Text at 200%. The demo base styles move from 16px to 1rem, so the fragment's text scales with the root. Fragments that size text in pixels do not scale. That is what 1.4.4 is about, and the new example relies on it.

5. The screen reader list

Decided: computed at build time, not live in the frame. A live list would need an accessible name library bundled into every demo document and a second code path for every example state. The build-time list is simple, deterministic and testable, and its one limit (it shows the state after load) is stated on the page.

  • Where. A server-only module, src/content/reading-order.ts, loads each variant's fragment into jsdom and walks it with dom-accessibility-api (getRole, computeAccessibleName), the library Testing Library uses. It runs in the loader that already parses the examples, once per build, and the result is prerendered into the page.
  • What it produces. Two lists per variant. "Czytanie po kolei": text runs and named elements in document order, with the role in Polish (przycisk, łącze, nagłówek, poziom 2, grafika, tabela, 3 kolumny, pole edycji). An element with an onclick and no role is marked "tekst, nie przycisk". "Kolejność Tab": the focusable elements in tab order, with role and name, or "bez nazwy".
  • What it skips. hidden, aria-hidden="true", display: none from the fragment's own styles, and images with alt="".
  • The hand-written line stays. announces in each example's frontmatter is still the one-sentence summary under the frames. The computed lists add the detail.
  • Shape. { reading: Line[]; tab: Line[] }, with Line = { text: string; role?: PolishRole; missing?: "rola" | "nazwa" }. PolishRole is derived from the role map, so a role without a Polish name fails tsc.

6. Content format

Simulator descriptions follow the rest of content/: one Markdown file per kind, frontmatter validated by ArkType.

content/symulatory/barwy.md
---
title: Widzenie barw
summary: Kiedy kolor jest jedyną informacją.
criteria: ["1.4.1", "1.4.11"]
examples: [formularz-z-bledami, kontrast-stanow]   # "Wypróbuj na", with the simulation preselected
limits: Nie pokazuje słabszych odmian zaburzeń ani tego, jak ktoś rozpoznaje kolor po kontekście.
status: szkic
---
General description, shown under the picker when an example has no note of its own.

Per-example notes go into the example's existing frontmatter, keyed by SimulationId:

# content/praktyka/formularz-z-bledami/index.md
simulations:
  deuteranopia: Czerwona ramka pola w wersji zepsutej wygląda jak oliwkowa i przestaje znaczyć „błąd”…
  protanopia: …

Notes are optional. I write them where a simulator shows something specific to the example: colour on the form, low vision on the contrast example, narrow screen on the new one. About ten notes. The keyboard, screen reader and narrow-screen simulators produce their own text, so they rarely need one.

The new example, content/praktyka/sztywna-szerokosc/: a delivery info card with a fixed width and white-space: nowrap, and a button with a fixed pixel height and overflow: hidden that clips its label at 200%. The fixed variant uses max-width, wrapping and min-height. Criteria 1.4.10 and 1.4.4, effort "1 token".

8. Accessibility of the simulators

  • Picker. A fieldset with native radios in a list, each label at least 44 pixels high with the name and one line of description. The picked option is marked with a tick and bold text, not colour alone. Changing a radio does not move focus.
  • Announcement. Picking a simulation announces "Symulacja: deuteranopia" once in a polite live region. The description is on the page, not announced, so the reader decides whether to read it.
  • Not colour alone. The label on each frame ("Deuteranopia") repeats the choice in text. Verdicts, missing roles and blocked clicks carry a word and a glyph.
  • Frame titles. The iframe title gains the simulation, for example "Przykład zepsuty: Formularz z błędami, deuteranopia".
  • Narrow frames scroll. A 320-pixel region that overflows is focusable and labelled, so its horizontal scroll works from the keyboard (2.1.1).
  • Forced colours. In Windows forced colours mode the filters change little, because the system replaces the colours. The note says so.
  • Motion. No transitions between modes. The blur is static.

9. Tests

  • Content (Vitest): every simulator kind has a file and every file parses; examples in simulator files and simulations keys in example files resolve; drafts carry no lastVerified.
  • Reading order (Vitest): a button with aria-label gives "Zamknij komunikat, przycisk"; a div with onclick gives text marked "tekst, nie przycisk" and no Tab stop; alt="" and aria-hidden are skipped; a table reports its columns. Every variant of every example computes without throwing and gives a non-empty reading list.
  • Frame channel (Playwright on /demo/...): after the simulation message the document has data-symulacja; in keyboard mode a mouse click on the broken close control does nothing and shows the notice, while Enter on the fixed button still closes the message.
  • End to end (Playwright): the definition of done, keyboard only. Open formularz-z-bledami, pick "Widzenie barw" and then "Deuteranopia" with the arrow keys; the URL has ?symulacja=deuteranopia, the note is visible, a reload keeps it. On ikona-jako-przycisk in keyboard mode, Tab into the fixed frame lists one step. On sztywna-szerokosc at 320px the broken variant says "Nie mieści się" and the fixed one "Mieści się". The existing isolation test runs once more with a simulation on.
  • Axe: /symulatory, and one example page with each kind picked.
