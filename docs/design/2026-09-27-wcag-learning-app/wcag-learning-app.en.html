1. Product goal

One place where somebody building a digital product in Poland learns three things: what a WCAG criterion actually says, what it looks like in code, and which Polish statute requires it of them. Today those three layers sit in three different places: the standard on w3.org, the explanations in the Understanding documents, the obligations in the Journal of Laws. The app stitches them together.

Three questions the user should be able to answer in two clicks:

  • I have a UI element and something is wrong with it. Which criterion covers this and how do I satisfy it?
  • I am a public body, or I sell a product in the EU. What do I have to do, and by when?
  • I know the criterion by name but the normative text is opaque. Explain it plainly, with an example.

This is not an auditing tool for other people's sites. Auditing is what axe, Lighthouse and manual testing are for. This is learning material with a practical layer.

2. Confirmed decisions

Leaving out the live editor is a deliberate narrowing. An editor is a separate problem: sandboxing, in-browser bundling, running axe against the result. Bolted onto the first version it would delay everything else. We keep the door open: the component that renders an example takes the code as a parameter, so swapping the code source for an editable field later is a change in one place.

3.2 The WCAG 3.0 module

WCAG 3.0 changes the model: instead of success criteria with a hard pass or fail, it introduces foundational requirements, outcomes and assertions, and the conformance model is still being argued out in the working group. Concepts from earlier drafts, such as bronze, silver and gold levels, have been dropped or rewritten. The conclusion for this plan: we do not teach 3.0, we show how the model differs and track the changes.

The module carries three things: a short explanation of how 3.0 differs from 2.x, a table of "what corresponds today to outcome X in 3.0" linking to 2.2 criteria, and one sentence on status with a date. Every page in this module shows a visible warning that the content may change, plus its lastVerified value.

3.4 Out of scope for the first version

  • A live code editor and on-the-fly auditing.
  • The W3C Techniques and Failures documents in full. We link, we do not copy. Selected techniques feed the "how to satisfy it" section, rewritten in our own words.
  • Law outside Poland and the EU.
  • Producing our own video and audio description. The 1.2.x criteria are of course covered, but with third-party examples.
  • ATAG and the WAI-ARIA Authoring Practices as separate modules.

4.1 The criterion page

The most important screen in the app. A fixed section order, so it can be read by habit:

  1. Header: number, name, level, version, a "new in 2.2" or "obsolete" badge.
  2. In one sentence: what this is about, no jargon, up to 200 characters.
  3. Who this affects: concrete user situations, not a list of disability labels.
  4. Normative text: the official translation, collapsed by default, with a link to the source and a toggle to the English original.
  5. How to satisfy it: concrete actions, grouped by role.
  6. Common failures: what Understanding scatters across its Failures documents.
  7. Examples: at least one bad and one good, side by side.
  8. How to test it: a manual procedure in steps, plus what an automated tool flags and what it misses.
  9. Law: which provisions require this, as links.
  10. Related criteria and common confusions ("this is not 1.3.1, it is 4.1.2, because…").
  11. Sources: links to WCAG, Understanding, techniques, and the last review date.

5. Content as code

Content lives in src/content/, one file per criterion and one per provision. The files are TypeScript modules rather than JSON or loose MDX, because we want a wrong id or a dead criterion reference to break tsc, not production.

5.1 Shape of the types

The rule: define data as const objects and derive the types from them, not the other way round. No any, no casts, identifiers as unions derived from the registry.

// src/content/wcag/criteria/1.1.1.ts
import { defineCriterion } from "../define";

export default defineCriterion({
  id: "1.1.1",
  slug: "tresc-nietekstowa",
  name: "Treść nietekstowa",
  level: "A",
  since: "2.0",
  principle: "postrzegalnosc",
  guideline: "1.1",
  inOneSentence: "Każda treść, która nie jest tekstem, potrzebuje tekstowego odpowiednika.",
  roles: ["dev", "design", "content"],
  howTo: [ /* ... */ ],
  commonFailures: [ /* ... */ ],
  examples: ["alt-dekoracyjny-vs-informacyjny", "ikona-jako-przycisk"],
  testing: {
    manual: [ /* ... */ ],
    automated: { catches: [ /* ... */ ], misses: [ /* ... */ ] },
  },
  legalRefs: ["ustawa-2019-848/zal-1", "en-301-549/9.1.1.1"],
  related: ["1.4.5", "4.1.2"],
  sources: [ /* ... */ ],
  lastVerified: "2026-09-27",
});
// src/content/wcag/define.ts
export const defineCriterion = <const T extends CriterionInput>(c: T) => c;

// src/content/wcag/registry.ts  (script-generated, not hand-written)
import c111 from "./criteria/1.1.1";
// ...
export const criteria = [c111, /* ... */] as const;
export type Criterion = (typeof criteria)[number];
export type CriterionId = Criterion["id"];   // "1.1.1" | "1.2.1" | ...

Deriving CriterionId from the registry means related: ["1.4.5"] stops compiling the day somebody deletes 1.4.5. The same holds for examples, legalRefs and path identifiers. A content change propagates through the types instead of requiring a manual sweep through files.

5.2 Content validation

Types catch shape, but they do not catch rules like "the one-sentence summary may not exceed 200 characters" or "an AA criterion must have at least one example". That is ArkType plus a single test that walks the whole registry, run in CI, so an empty section cannot land on master.

5.3 Longer prose

Narrative sections (lessons, act summaries) live as MDX next to the criterion file and are imported into the object. Short fields stay in TS so they can be filtered and indexed without parsing MDX.

5.4 Search

The index is built at build time from the registries and written out as a static file, lazily loaded on the /szukaj route. MiniSearch or FlexSearch. No search backend, no Convex queries. Tuned for Polish: no stemming, prefix matching with typo tolerance, plus manual aliases ("focus" to "fokus", "alt" to "tekst alternatywny", "aria-label").

6. Plain-language module

This is the actual reason the app exists. The W3C Understanding documents are good and exhaustive, but they are written for people who already understand the standard. Our version has a different goal: somebody reads one screen and knows what to do.

6.1 Writing rules

  • User situation first, requirement second. "Somebody using a screen reader lands on a button and hears only the word button" before "the control must have an accessible name".
  • No jargon without explanation. The first use of a term links to the glossary.
  • Always the concrete number when the standard gives one. "4.5 to 1", not "sufficient contrast".
  • The "how to satisfy it" section is imperative verbs, not a description of a target state.
  • Split by role for criteria that involve several people. 1.4.3 is one job for a designer and another for a developer.

6.2 Glossary

A separate registry of terms defined in Polish: accessible name, accessibility tree, focus, live region, forced colours mode, pointer target, mechanism. Rendered as a disclosure at first occurrence and available as its own page. Where the normative definition differs from everyday usage, we show both.

6.3 Where the content comes from

Numbers, names, levels and guideline membership are imported once by a script from the data W3C publishes, so there are no typos in structured data. All prose is written from scratch. Two reasons: the licence, and the fact that a rewritten Understanding would not be simpler than Understanding.

7. Legal module and mapping

7.1 Act structure

An act is not one long text but a tree of provisions, because a mapping has to point at a specific paragraph, not at a PDF.

src/content/legal/
  ustawa-2019-848/          digital accessibility of public bodies
    act.ts                  metadata: title, Journal of Laws, date, who it binds, deadlines
    units/art-5.ts          { id, label: "Art. 5 ust. 1", text, plainSummary }
    units/zal-1.ts
    summary.mdx
  ustawa-2019-1696/         persons with special needs
  ustawa-2024-731/          Polish Accessibility Act (EAA transposition)
  en-301-549/               clauses as units, the mapping link
  dyrektywy/                2016/2102 and 2019/882, summaries and context only

Each unit has two text fields: text with the literal wording of the provision and plainSummary with a human explanation. We show the explanation by default and the literal text on expand. The other order loses the reader after two sentences.

7.2 Mapping

The relation is many-to-many and read from both sides, so we keep it in one place and generate indexes in both directions instead of duplicating lists on either end.

// src/content/mapping/edges.ts
export const edges = [
  { legal: "ustawa-2019-848/zal-1", criterion: "1.1.1", strength: "wprost" },
  { legal: "en-301-549/9.1.1.1",    criterion: "1.1.1", strength: "wprost" },
  { legal: "ustawa-2024-731/art-8", criterion: "1.4.3", strength: "posrednio",
    note: "Przez odesłanie do norm zharmonizowanych." },
] as const satisfies readonly MappingEdge[];

strength has three values: wprost (direct) when the provision names the criterion, posrednio (indirect) when it reaches it through a harmonised standard, powiazane (related) when it is context rather than an obligation. Without that distinction the app would imply that the act mandates AAA criteria, which it does not.

7.3 The mapping screen

Not an 86-by-200 matrix, because nobody reads that. Instead you pick your situation (public body, commercial product in the EU, both) and the app shows a list of obligations with deadlines and an expandable list of criteria under each. The full table stays available behind a toggle, for people who genuinely want the grid.

7.4 Obligations timeline

A vertical list of dates with a note on what starts or stops applying on each. No chart, since there are a dozen or so points. Each point links to the provision the date comes from.

8. Practice: examples, simulators, quizzes

8.1 Bad and good examples

One example is an object with two variants, a short note on the difference, and a note on what a screen reader says in each. Rendered as two columns on a wide screen, stacked on a narrow one, with a tab for the code.

Important technical decision: the bad example is rendered inside a sandboxed iframe, not inline. An inaccessible fragment injected straight into the document poisons the accessibility tree of the whole app, and the user's screen reader would meet an unnamed button and an out-of-hierarchy heading in the middle of a page about accessibility. The iframe isolates the tree, carries its own title, and sits next to a text description of what is broken inside it. The good variant can be inline.

A starter set, one example per common situation: decorative versus informative alt text, an icon used as a button, a modal and a focus trap, a form with errors and an error message, a data table with headers, a custom dropdown versus a select, an auto-playing carousel, contrast on hover and disabled states, a 24-by-24-pixel touch target, dragging with a click alternative.

8.2 Impairment simulators

SimulatorHowWhat it teaches

Simulators operate on examples inside the app, not on arbitrary pages. Two rules: they are never the only carrier of information, since that would make the module itself fail 1.4.1, so a text description always accompanies the filter. And they are never on by default.

8.3 Learning paths

A path is an ordered list of lessons, where a lesson points at criteria, examples and a quiz. Four to begin with, by role: developer, designer, content author, tester. A fifth, cross-cutting one, "legal minimum for a public body", walks through the criteria in the annex and through the accessibility statement.

Paths are linear and ungated. We do not require a quiz before reading on, because this is material for adults at work, not a certificate course.

8.4 Quizzes

Question types: single answer, multiple answers, "which criterion does this code break" with the snippet shown, "point out the fault in this interface" with a list of elements to choose from. Every answer, correct ones included, comes with an explanation and a link to the criterion. The result is announced in a live region so a screen reader reads it without a focus move.

No points, badges or streaks. Progress is information about where you stopped, not a mechanic.

9. Convex: user data

Convex holds only what belongs to a specific person. Content never enters the database.

convex/schema.ts

users          { subject, displayName, createdAt }               // subject from the auth provider
progress       { userId, lessonId, status, updatedAt }           // read, completed
quizAttempts   { userId, quizId, answers, score, completedAt }
notes          { userId, targetType, targetId, body, updatedAt }  // note on a criterion or provision
bookmarks      { userId, targetType, targetId, createdAt }

targetId is validated in the mutation against the content registry, so a note cannot be saved against a criterion that does not exist. Indexes on userId plus targetId, since every query is scoped to one user.

Authentication: Clerk as the default, well integrated with both Convex and TanStack Start. If this has to be self-hosted, better-auth. The entire app is readable without signing in. Signing in only enables progress, notes and bookmarks, so a first visit does not open on a signup screen.

11. Accessibility of the app itself

The baseline from docs/accessibility.md: WCAG 2.2 Level AA, plus 2.3.3 and 2.5.5 at AAA. For this app specifically we go higher where it is cheap, because otherwise the content would not be credible.

  • AAA on purpose for 1.4.6 (Contrast Enhanced) and 2.4.13 (Focus Appearance). Contrast and focus are the first things anybody will check in an app about accessibility.
  • Touch targets at 44 by 44 pixels, not 24, everywhere.
  • Skip link, a stable landmark structure, one h1 per page, no skipped heading levels.
  • Route changes announced in a live region and focus moved to the heading, because a single-page app does not do this by itself.
  • prefers-reduced-motion honoured. No continuously repainting animation.
  • No information carried by colour alone. Levels A, AA and AAA pair colour with text and shape.
  • Windows forced colours mode verified, because some users of this app will be using it.
  • An accessibility statement as a subpage, written to the requirements of the act. It doubles as an example and links to the lesson about statements.

12. Tests and CI

  • Content invariants (Vitest, one walk over the registries): every criterion has a one-sentence summary, a how-to section and a source. Every AA criterion has an example. Every mapping edge points at an existing provision and an existing criterion. Every identifier in related, examples and legalRefs resolves. Every act and criterion has lastVerified. These are the most valuable tests in the project: they guard the content the compiler does not.
  • Accessibility (Playwright plus axe-core) over a representative set of routes, not all 86 criterion pages. A separate test asserts that the bad example stays inside its iframe and does not leak into the page's accessibility tree.
  • Keyboard: a pass over the main flows without a mouse, including the quiz and the list filters.
  • Manual, because it cannot be automated: NVDA with Firefox and VoiceOver with Safari, on a checklist before each release. Kept in the repo as a list of steps, not as a test.
  • CI: pnpm lint, pnpm build, pnpm test, plus axe against the preview.

13. Licences and sourcing

W3C documents (WCAG 2.1, 2.2, Understanding, the Polish translation)
Covered by the W3C Software and Document License, which permits redistribution with attribution and the notice preserved. Strategy: quote verbatim only the text of the success criteria, clearly marked and linked. Write our own explanations. Do not copy Understanding or the techniques wholesale. The exact wording of the notice to be confirmed at first import.
WCAG structured data
Numbers, names, levels and guideline hierarchy imported once by a script in scripts/ from the data W3C publishes. The script is run by hand and its output approved in a PR. The app fetches nothing at runtime.
Polish legal acts
Normative acts and their official drafts are not subject to copyright, so we may store and quote the full text. The source is the consolidated text from ISAP, with the retrieval date recorded. Our own summaries are marked as ours, so nobody mistakes them for the wording of the law.
EN 301 549
A harmonised standard, publicly available from ETSI but on different terms from legal acts. We store clause numbers and titles plus our own summaries, without the full text. To be confirmed before the legal phase.
Disclaimer
The /o-projekcie page states plainly that the legal module is educational material, not legal advice, and that the binding wording is the one in the Journal of Laws. Every provision page shows its verification date.

16. Decisions needed before we start

  1. Public or private. If the app is public, the legal module needs a more careful disclaimer and the content a higher editorial bar. If it is a tool for you and your team, we can write faster.
  2. Hosting. The choice between Netlify, Vercel and Cloudflare affects prerendering in TanStack Start. Convex is independent of it.
  3. Authentication. Clerk or better-auth. It only matters from phase 5, so the decision can wait.
  4. Who writes the content. You write it, I draft it for your edit, or we mix. This changes the pace of phases 2 and 4 more than anything technical.
  5. How much statute text. Every article of all three acts, or only those that create digital obligations. The full text of the 2024 act is a great deal of content, some of which has nothing to do with interfaces.
  6. Visual mocks. Before phase 0 exists, the criterion page and the mapping screen should go through several static variants for you to pick from. That is a separate task, not part of this plan.
