1. Goal and definition of done

After phase 2 the app is useful on its own for anyone who needs Level AA: every A and AA criterion of WCAG 2.2 has a plain-language explanation, the terms that block understanding are explained where they appear, and you can find a criterion by typing what is wrong with your interface.

Done when:

  • An A or AA criterion without a complete content file fails pnpm test.
  • Every page with draft content says so visibly.
  • Searching "modal", "alt" or "kontrast" returns the right criteria.
  • A term marked in a criterion's text opens its definition preview from the keyboard, and the term itself links to the glossary.

3. Changes to the content format

3.1 Status

A new required field, status, with two values. lastVerified becomes required only once a person has checked the content, so the app never claims a verification that did not happen.

---
status: szkic            # or: zweryfikowane
summary: ...
roles: [programista, projektant]
related: ["1.4.11"]
keywords: [kontrast, szary tekst, placeholder]   # new, optional, feeds search
lastVerified: 2026-10-14 # required when status is zweryfikowane, forbidden otherwise
---

A draft shows a badge in the page header: dashed border, a pencil glyph and the words "szkic, czeka na weryfikację", so it does not rely on colour. It is visible in all three glossary mocks. The list shows the same marker next to the level.

You review a file, change status to zweryfikowane and add the date. That edit is the whole review workflow.

3.2 Completeness

An A or AA criterion must have a file with summary, roles and at least the sections Kogo to dotyczy, Jak to spełnić, Typowe błędy and Jak sprawdzić. Częste pomyłki stays optional, because not every criterion has a common confusion worth a section. AAA files stay optional until phase 8.

3.3 Glossary links

An author marks a term explicitly: [nazwę](slownik:nazwa). The parser resolves the slug against the glossary and fails on an unknown one, exactly as it does for related. We do not match terms automatically: Polish inflects nouns (nazwa, nazwę, nazwy), so matching would either miss or produce false hits. Only the first marked occurrence on a page gets the glossary treatment; later ones render as plain text, so a page does not turn into a sea of underlines.

4. Writing 55 criteria

I write the drafts; you review and flip the status. The writing rules from section 6.1 of the main plan apply unchanged: the user's situation first, the concrete number whenever the standard gives one, imperative verbs in "Jak to spełnić", split by role where several people are involved.

For each criterion I work from the W3C Understanding document and the sufficient techniques and failures, and rewrite in my own words. Nothing is copied from Understanding, both for the licence and because a translated Understanding would not be simpler than Understanding. 1.4.3 is the reference for length and tone: roughly 250 to 450 words per criterion.

Order: by principle, one commit per principle, so the history and the review can go one principle at a time inside a single pull request.

5. Normative text

The "Treść normy" section on the criterion page is filled from the authorized W3C translation of WCAG 2.1. pnpm import:wcag gains a step that extracts the text of each criterion, including its lists of exceptions and notes, into wcag.gen.ts as a small whitelisted subset of HTML (paragraphs, lists, emphasis). Links inside the text point to our glossary where we have the term, and nowhere otherwise. The section stays collapsed by default, with a line naming the source.

Six A and AA criteria are new in 2.2 and have no authorized Polish text: 2.4.11, 2.5.7, 2.5.8, 3.2.6, 3.3.7 and 3.3.8. For those the section links to the IRDPL translation and to the W3C specification instead of quoting, until IRDPL confirms the licence. After that, the text is quoted with attribution to IRDPL.

6. Glossary

6.1 Format

One file per term in content/slownik/<slug>.md, validated by the same parser pattern:

---
term: nazwa
also: [dostępna nazwa]          # everyday names, shown and searchable
normative: nazwa                # the entry in the WCAG glossary, when there is one
status: szkic
---
To, co czytnik powie o kontrolce, zanim powie, czym ona jest: „Zamknij okno, przycisk”.
Nie myl z atrybutem `name` w HTML.

The normative definition, when normative is set, is imported with the rest of the W3C translation in section 5, not typed by hand. The criteria listed under an entry are computed from the slownik: links in criterion files, so they never drift.

6.2 Starting set

About 30 terms, picked from what blocks understanding in the 55 criteria: nazwa, rola, wartość, stan, fokus, kolejność fokusu, interfejs klawiaturowy, pułapka na klawiaturę, czytnik ekranu, technologie wspomagające, drzewo dostępności, określone programowo, komunikat o stanie, zmiana kontekstu, etykieta, instrukcja, tekst alternatywny, treść nietekstowa, stosunek kontrastu, duży tekst, cel, wskaźnik, gest wielopunktowy, mechanizm, alternatywa dla mediów, napisy rozszerzone, audiodeskrypcja, blok treści, relacje, sekwencja znacząca.

6.3 Rendering and the page

Picked from glossary-mocks.html: C for a term in text and D for /slownik.

  • Term in text (C). The term is an ordinary link to its anchor on /slownik, so it works without JavaScript. Next to it, a toggletip button opens the short definition: aria-expanded on the button, content announced in a status region, Esc and a 44px close button dismiss it, focus stays on the button. The preview is positioned so it never covers the focused element (2.4.11) and flips above the text near the bottom of the viewport. The 24px button relies on the inline-target exception of 2.5.5.
  • Glossary page (D). One alphabetical page with a letter index. Letters without terms are plain text. Each entry: the term as a heading, everyday names, the plain explanation, the normative wording, and the criteria where it appears.

7. Search

  • Index at build time. A server route, /search-index.json, builds the index from the criteria and glossary content, and prerendering writes it out as a static file. No separate script, no search backend. /szukaj loads it lazily, so no other page pays for it.
  • Engine: MiniSearch. Fields: number, name, summary, keywords, section text, and glossary term with its also names. Prefix matching and light typo tolerance.
  • Polish: no stemming. Terms are lowercased and diacritics are folded, so "zrodlo" finds "źródło". Symptom words ("modal", "karuzela", "placeholder") come from keywords, written with the content.
  • Page: follows screen 7 of variant A, with one change. The field gets a visible label instead of relying on the placeholder, because our own content lists a placeholder used as a label as a typical error. The form is role="search", submits by GET to /szukaj?q=, and the result count is announced in a status region. Results are grouped: criteria, glossary.
  • Home page: the search field from screen 0 of variant A, submitting to /szukaj.
  • Without JavaScript: the page explains that search needs JavaScript and links to the criteria list and glossary.

8. Role filter

With every A and AA criterion carrying roles, the role filter from screen 1 of variant A comes back: checkboxes for programista, projektant, autor treści and tester, in the URL like the other filters. Criteria without content (AAA for now) do not match any role, and the "applied filters" line says so, so a user filtering by role does not think AAA criteria vanished.

9. Tests

  • Content (Vitest): completeness of every A and AA criterion; lastVerified present exactly when status is zweryfikowane; every slownik: link resolves; every glossary normative key exists in the imported WCAG glossary; verified content older than an agreed age fails (section 12).
  • Search (Vitest): a short table of queries and expected first results, including a folded diacritic and a keyword. It guards relevance when content changes.
  • Accessibility (Playwright and axe): /szukaj with results and with none, /slownik, a criterion page with an open definition preview, and one draft page. A test checks that the open preview does not overlap the focused button.
  • Keyboard: type a query and reach the first result; open and close a definition; filter the list by role.

10. Commits and the pull request

One pull request for the whole phase, on a branch feat/criteria-content, with commits in this order so every one passes lint, build and tests:

  1. feat(content): add draft status and keywords to criterion content, with the badge on the page and in the list.
  2. feat(content): import normative text of WCAG 2.1 in Polish, the script change.
  3. chore(content): regenerate WCAG data with normative text, the generated file alone.
  4. feat(glossary): add glossary format and term links in content.
  5. docs(glossary): write the starting set of terms.
  6. docs(content): explain A and AA criteria of principle 1, then the same for principles 2, 3 and 4, four commits.
  7. test(content): require complete content for A and AA criteria. It lands after the content on purpose: earlier it would fail the commits in between.
  8. feat(glossary): render terms in text and add the glossary page, variants C and D.
  9. feat(criteria): add role filter.
  10. feat(search): add search page, index and home search field.
  11. docs: update README for phase 2, with new screenshots.

12. Decisions

  • Glossary variants: decided. C for a term in text, D for the glossary page.
  • Maximum age of verified content: decided. 12 months, after which a test fails and the criterion needs a fresh check.
  • IRDPL text for the six new criteria: decided. IRDPL, Polska Izba Rzemiosła Dostępnościowego, translates WCAG 2.2 as a community project; the translation is not authorized by W3C. We quote it with attribution once IRDPL confirms the licence. Until then the section links to IRDPL and W3C.
