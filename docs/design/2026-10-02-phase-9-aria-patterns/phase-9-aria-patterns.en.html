Plan: phase 9, ARIA widget patterns

A phase outside the main plan. Scope taken from the 30 entries of Deque University ARIA Examples. Mocks of the pattern page, the catalogue, the live region playground and the entry point: aria-patterns-mocks.html. Plan version: 2026-10-02, changes 2026-10-03.

"Symulatory" already means the impairment simulators from phase 7 (/symulatory, ?symulacja=). These widgets are a different thing: working components you operate and listen to. This plan calls them wzorce (patterns) and puts them at /wzorce, so one word keeps one meaning. Decision 1.

We do not copy Deque's code. The Deque library has no open licence; its pages fall under Deque's terms of use. Each pattern is written by us from the WAI-ARIA Authoring Practices Guide (APG, W3C), and links to the Deque page and the APG pattern as further reading.

Changes after work started

Decisions made while building the pull requests so far. Where they conflict with the sections below, these win.

  • Patterns live inside Praktyka (sections 7, 12). Mock 4B puts them under the Praktyka heading, so the routes are /praktyka/wzorce and /praktyka/wzorce/$slug, not /wzorce. The header keeps "Praktyka" current on them without new code. Demo documents stay at /demo/wzorce/$slug.
  • The exercise replaces the keyboard table (sections 6, 9). With mock 1C the frontmatter has steps instead of keyboard: what to do, the keys, and the log line to hear. The first step must start with Tab, which enters the frame. The Playwright test presses each step's first key on the real page and expects every step ticked, so the walk table in section 9 is the content itself.
  • The log is inlined, not /demo/wzorce/log.js (section 5). A Vite plugin builds it with dom-accessibility-api into one classic script, served as virtual:pattern-log, and every pattern document inlines it. About 22 KB minified, under the 30 KB limit from section 11.
  • Generated content is left out of names (section 5). dom-accessibility-api does not understand CSS alt text (content: "+" / "") and would read "+" in a button's name. Our patterns give generated content empty alt text anyway.
  • State words are neuter (section 5). "zwinięte", "zaznaczone", "naciśnięte", like the build-time reading order, not "zwinięty".
  • ARIA rows carry a selector (section 6). selector tells the frame which element to read for the "Teraz" column. A test checks that every selector matches an element of its fragment.
  • One "Kod" disclosure, not three (section 7). A fragment is one file, as in the practice examples.
  • The keyboard-only toggle is a checkbox (section 7). It is local to the page, not ?symulacja=. A blocked click is counted under the frame and announced once, as on example pages.
  • Two more refactor commits (section 10). The iframe plumbing moved into useDemoFrame, and the ## section splitter into render.ts, so pattern pages and pattern files reuse them. legend now reads as plain text in the build-time reading order.
  • Batch 2: the log reads descriptions and popovers (section 5). Focus lines end with the accessible description (aria-describedby), which is how a tooltip's text and an alert dialog's message get read; a container entered with a description reads it too. A button with popovertarget reads expanded or collapsed from its popover, which changes no attribute.
  • Batch 2: native first where it now exists (section 3). The tooltip dialog is a popover with role="dialog"; the browser closes it with Esc and hands focus back. Both dialogs are dialog with showModal(), the alert dialog with role="alertdialog". Both accordions keep the button in a heading, because details loses the heading inside summary.

1. Goal and definition of done

The practice section shows what goes wrong. Phase 9 shows what right looks like for the components people build by hand: an accordion, tabs, a slider, a combobox, a date picker. The reader operates each one with the keyboard and sees, next to it, what a screen reader would say after every key press and which ARIA attributes changed.

Done when:

  • All 30 patterns from section 3 run on /wzorce/$slug, each in a sandboxed frame, each operable with the keyboard alone.
  • Every pattern page has a keyboard table, an ARIA table, the criteria it serves, and a log of announcements that fills in as the reader interacts.
  • Where a native element does the job (button, a, input type="checkbox", details, progress), the page says so before any ARIA, and the pattern uses it.
  • Axe passes on every pattern frame in both themes, and a Playwright test walks every pattern with the keyboard and checks the state attributes.
  • /wzorce lists the patterns, and criterion pages and practice examples link to the patterns that show them.

4. Native element first

The first rule of ARIA is not to use it when HTML has the element. A catalogue of 30 ARIA widgets can teach the opposite by accident, so every pattern page opens with one of three verdicts, in text and with a glyph:

  • Wystarczy HTML. The native element does everything. The pattern uses it, and the page shows what the browser gives for free (button, link, checkbox, details, progress).
  • HTML z dodatkiem ARIA. A native base with one or two attributes on top: the toggle button with aria-pressed, the sortable table with aria-sort.
  • Tylko ARIA. HTML has nothing equivalent: tabs, tree, combobox, the date grid. The page says what the author now owes: every key and every state.

The verdict is a frontmatter field, so /wzorce can filter by it, and the catalogue shows how few patterns need ARIA alone.

5. What a screen reader would say, live

Phase 7 rejected a live list and computed the reading order at build time. For widgets that decision does not hold, because a pattern is its state changes. Pressing Enter on an accordion header matters because aria-expanded flips and the reader hears "rozwinięty". So pattern frames get a live log, and practice examples keep the build-time list.

  • Where it runs. Inside the frame, in a script added to pattern demo documents only. It uses dom-accessibility-api (computeAccessibleName, getRole), the library the build-time list already uses, bundled once into /demo/wzorce/log.js and loaded by every pattern frame. The sandbox stays allow-scripts allow-forms with an opaque origin. Decision 3.
  • What it logs. Three kinds of line, posted to the page as { a11yAnnounce: { kind, text } }:
    • focus: on focusin, the name, the Polish role and the states, for example "Dostawa, przycisk, zwinięty". Also when aria-activedescendant moves, which is how the combobox and the date grid move their focus.
    • state: a MutationObserver on the focused element for aria-expanded, aria-checked, aria-pressed, aria-selected, aria-valuenow, aria-valuetext, aria-sort, aria-current and the native checked, open and value. Only the focused element, because that is what screen readers announce.
    • live: text added inside aria-live, role="status", alert or log, marked "grzecznie" (polite) or "natychmiast" (assertive), respecting aria-atomic.
  • The ARIA table follows along. The same script posts { a11yState: Record<string, string> } for the attributes the pattern's frontmatter lists, so the "Teraz" column shows current values.
  • The page does not speak. The log is an ordered list, not a live region, for the same reason as the focus trace in phase 7: it would talk over the reader's own screen reader. A "Wyczyść" button empties it.
  • Polish names. The role map from reading-order moves to a shared module. States get the same treatment: a typed stateLabels map, so aria-expanded="false" reads "zwinięty" everywhere.
  • Limits, stated above the log. Real screen readers differ in wording, order and timing; some announce aria-live changes late or not at all; browse mode is not simulated. The log answers "what does the code expose", not "what will JAWS say".
// src/content/announce.ts, shared by the frame script and the page
export const announceKinds = { focus: "Fokus", state: "Zmiana", live: "Region na żywo" } as const;
export type AnnounceKind = keyof typeof announceKinds;

export const Announce = type({
  a11yAnnounce: { kind: "'focus' | 'state' | 'live'", text: "string", "politeness?": "'polite' | 'assertive'" },
});

6. Content format

One folder per pattern, shaped like the practice examples:

content/wzorce/
  akordeon-pojedynczy/
    index.md        frontmatter, then "Kiedy używać", "Typowe błędy", "Jak sprawdzić"
    wzorzec.html    the fragment: markup, style, script
---
title: Akordeon, jedna sekcja
en: Accordion (Single)
batch: pokazywanie
native: html-i-aria            # html | html-i-aria | tylko-aria
summary: Lista nagłówków, z których każdy rozwija swoją sekcję. Otwarcie jednej zamyka poprzednią.
criteria: ["1.3.1", "4.1.2"]
keyboard:
  - keys: [Enter, Spacja]
    action: Rozwija albo zwija sekcję pod nagłówkiem.
  - keys: [Tab]
    action: Przechodzi do następnego nagłówka albo do treści otwartej sekcji.
aria:
  - attr: aria-expanded
    on: przycisk w nagłówku
    meaning: Czy sekcja jest otwarta.
  - attr: aria-controls
    on: przycisk w nagłówku
    meaning: Która sekcja należy do przycisku.
sources:
  apg: https://www.w3.org/WAI/ARIA/apg/patterns/accordion/
  deque: https://dequeuniversity.com/library/aria/accordion-single
status: szkic
---
  • ArkType validates it. keys come from a typed list (Enter, Spacja, Tab, Shift+Tab, the arrows, Home, End, PageUp, PageDown, Esc, letters), so a typo fails the build. attr comes from the list of attributes the log watches, so the "Teraz" column never points at something nobody reports.
  • criteria and the optional examples resolve against their registries, as everywhere else.
  • keyboard may be empty only where the pattern has no interaction of its own (the alert, the bounded progress bar). A test names the allowed ones.
  • Sections: "Kiedy używać" (including when the native element is enough), "Typowe błędy", "Jak sprawdzić". The first two are required.

8. Accessibility of the patterns

The patterns are teaching material, so each one meets docs/accessibility.md on its own, not only the page around it.

  • Targets. 44 by 44 pixels for every control in every pattern, including tree twisties, date grid cells, slider thumbs and carousel dots (2.5.5).
  • Focus. The app's 3-pixel outline inside the frames too (2.4.7, 2.4.13), and nothing that covers the focused element (2.4.11, 2.4.12): the tooltip opens beside its trigger, not over the next control.
  • Motion. The carousel does not rotate until the reader starts it, and never under prefers-reduced-motion. The unbounded progress bar has a static variant under reduced motion (2.2.2, 2.3.3).
  • Dragging. Sliders move with the arrows and with a click on the track; the multirange slider adds two number fields (2.5.7).
  • Hover content. The tooltip opens on focus too, stays while hovered, and closes with Esc without moving focus (1.4.13).
  • Forced colours. Custom states (the mixed checkbox, the selected tab, the sort direction, the selected date) show with a glyph or a border, not a background colour alone (1.4.1, 1.4.11).
  • Language. English names carry lang="en"; interface copy in the frames is Polish (3.1.2).
  • The log and the ARIA table are a list and a table with a caption. Changed rows are marked with a word ("zmienione") and a glyph, not colour.

9. Tests

  • Content (Vitest). Every pattern parses; slugs match section 3; criteria, examples, keys and attr resolve; every pattern has "Kiedy używać" and "Typowe błędy".
  • The log (Vitest, jsdom). The accordion fragment and a click on its header: the log reads "Dostawa, przycisk, zwinięty", then "rozwinięty". A polite and an assertive region: the right politeness and the atomic text.
  • Keyboard walks (Playwright). One table in e2e/patterns.spec.ts: per pattern, the keys to press and the attribute values expected after each. Thirty short walks, not thirty files.
  • Axe and target size. Every /demo/wzorce/<slug>, /wzorce and one pattern page in both themes join the routes list. Pattern frames are also checked open (dialog open, combobox expanded, date picker open), because axe sees only what is rendered.
  • Reduced motion. The carousel and the unbounded progress bar run no animation with reducedMotion: "reduce".
