Where things stand

The good part: every page is prerendered to HTML, so a crawler sees the full content without JavaScript. lang="pl" is set and most routes have their own title. Everything else is missing.

ItemPresent?Effect
meta descriptionnoGoogle cuts its own snippet from the page, often the navigation or a banner.
link rel=canonicalno/kryteria?poziom=AA, /praktyka/x?symulacja=czytnik and /praktyka/przed-i-po/lista?komu= are separate URLs with the same content to a crawler.

Scope

One file with the address and a head helper, two new routes prerendered as files, an image generator, and JSON-LD built from data the routes already load. None of it changes how pages look, apart from the favicon.

Head tags

One source for the address

src/lib/site.ts holds siteUrl = "https://a11y-playground-tau.vercel.app" and the site name. Changing the domain is one line. No environment variable: preview builds should also put production URLs in canonical, and Vercel already adds X-Robots-Tag: noindex to preview URLs (I will check this on one preview deploy, see manual steps).

The pageHead helper

src/lib/seo.ts exports a function that turns { title, description, path, image?, noindex? } into ready meta and links for a TanStack Router head: title, description, canonical, og:*, twitter:card, robots. The argument type takes the path from FileRoutesByPath, so a typo in path fails tsc. Canonical never carries a query or a trailing slash.

head: ({ loaderData }) => pageHead({
  title: `${c.id} ${c.name}, WCAG 2.2`,
  description: c.summary,
  path: `/kryteria/${c.id}`,
}),

Descriptions are cut to 160 characters at a word boundary. The summary fields already exist and run one or two sentences, so only the list pages need hand-written descriptions.

Titles

The X · a11y playground pattern stays. One change: criteria get "WCAG 2.2" in the title (people search "wcag 1.4.3", not "kontrast minimum"). The home page stays at a11y playground (decisions).

Favicon

No icon means a grey globe in Google results. This is a visual change, so it starts with mocks (2 or 3 variants of a simple mark, SVG plus a 180 px PNG for Apple) through html-communication, then your pick, then code. This step waits on the mocks and does not block the rest.

What goes into the index

PagesIndexSitemapWhy
every app page except those belowyesyes
/demo/* (bad/good variants, patterns, KMW przed, przed-znaczniki, po)noindexnoYour call. The app pages that frame them are indexed as usual.
/szukajnoindexnoA search results page. Google advises against indexing those.
/praktyka/przed-i-po/lista and /praktyka/przed-i-po/1 to /20noindexnoPrerender sees empty progress, so the HTML holds only "Najpierw sprawdź stronę sam". The entry page /praktyka/przed-i-po gets indexed.
/search-index.jsonn/anoNot HTML.

noindex on /demo/* documents goes in as <meta name="robots" content="noindex"> inside the document, not as an HTTP header. Prerender writes these pages as static files, and headers set in the handler are lost. The meta goes into demoDocument and the KMW document, not into the example markup, so it does not change what axe checks.

robots.txt and sitemap.xml

The prerender page list lives in vite.config.ts today. The sitemap needs the same list. Instead of a second copy, I move it to src/content/site-pages.ts and import it in both places. That is its own mechanical commit with no change in behaviour. Each entry gets an index: boolean field and the sitemap filters on it.

Both routes work like search-index[.]json.ts: a GET handler plus a pages entry with autoSubfolderIndex: false.

User-agent: *
Allow: /
Sitemap: https://a11y-playground-tau.vercel.app/sitemap.xml

No Disallow: /demo/. A crawler does not fetch a blocked page, so it never sees the noindex and may list the bare URL with no description. I will leave a comment in the code so nobody adds it later.

No lastmod. Without a real change date for each page, Google ignores it anyway.

Open Graph images

A 1200×630 PNG for every indexed page, made during prerender. A route /og/$[...]path.png returns the PNG; in site-pages.ts every page with index: true gets a second entry for its image.

  • Libraries: satori (JSX to SVG) and @resvg/resvg-wasm (SVG to PNG). The wasm build, not the native one, so the build behaves the same on Vercel and on Windows.
  • Font: satori cannot read woff2, and @fontsource-variable/inter ships only that. I add an Inter TTF (OFL licence) to src/assets/. It has to cover Polish letters; a test checks that.
  • Image content: the section (Kryteria, Praktyka, Prawo…), the page title, the A/AA/AAA level for a criterion, the site name. Text contrast at least 7:1, because the image lands in someone else's interface where we control nothing else.
  • og:image:alt repeats the page title, so a screen reader in Slack or LinkedIn has something to read.
  • The image design is a visual change. 2 or 3 variants go into the mocks together with the favicon first, then code.

Cost: one PNG per indexed page in the build and a longer prerender. I will measure both before committing. If the build grows too much, I fall back to one image per section instead of per page; that is a change to one function.

JSON-LD

The <script type="application/ld+json"> blocks go through scripts in head, with < written as <. Types come from schema-dts (types only, no code in the bundle), so a wrong property in a schema is a tsc error.

WhereTypeBuilt from
/WebSiteconstants. No SearchAction: Google dropped the search box in results in 2024.
pages with the "Okruszki" navigationBreadcrumbListthe breadcrumbs the page already shows
/slownikDefinedTermSet with a DefinedTerm per entryglossary.ts
/sciezki/$pathCoursepath title, description, lesson list
/sciezki/$path/$lessonLearningResource containing a Quizthe lesson and its questions
/prawo/$act, /prawo/$act/$unitLegislationact metadata from ELI (legislationIdentifier, consolidated text date)

To be honest about it: of these, Google shows a rich result today only for breadcrumbs. Course needs a filled-in offer and provider, and Google's Quiz support is limited to education content with answers in the HTML, so these types mostly give other search engines and tools a correct description. They cost little, since the data is already in the loaders.

Tests

All of them run against the built .output/public, in one file, either e2e/seo.spec.ts or a vitest test that reads files, no browser needed:

  • every URL in sitemap.xml exists as a file, has a canonical equal to itself and a non-empty description;
  • descriptions and titles are unique across sitemap pages;
  • no noindex page is in the sitemap, and every /demo/* document has noindex;
  • every og:image points at an existing 1200×630 PNG;
  • every JSON-LD block parses.

The pageHead helper gets one unit test for description cutting and canonical building. Nothing more is needed.

Decisions

QuestionDecision
KMW list and problem pagesnoindex, out of the sitemap. A crawler would see only the lock, and putting the content in the HTML would give the answers away.
Home page titleStays a11y playground, no tagline. The home page only gets a description.
"WCAG 2.2" in criterion titlesYes: 1.4.3 Kontrast (minimum), WCAG 2.2 · a11y playground. WCAG 3 items stay as they are.
Google Search ConsoleOutside the PR. It is not Google Analytics: it shows the index status and takes the sitemap, with no script and no cookies. You add the property yourself after deploy, using the HTML file method. Traffic analytics are not part of this plan.

Out of scope and manual steps

  • A custom domain. When it comes, I change siteUrl and you set a 308 redirect from *.vercel.app in Vercel.
  • An English version and hreflang. The site has one language.
  • Rewriting copy for keywords. Content stays as it is; this plan covers the technical side of indexing.
  • Your steps after deploy: add the property in Search Console and Bing Webmaster Tools, submit /sitemap.xml, run a few URLs through "URL Inspection".
  • My step before the PR: check on a preview deploy that Vercel sends X-Robots-Tag: noindex. If it does not, I add noindex keyed on VERCEL_ENV.
