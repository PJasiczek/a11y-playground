Plan: phase 10, landmarks and headings

Brief: a simulator and a practical exercise after the W3C page Landmark Regions, General Principles ("Show Landmarks", "Show Headings"). Mocks: landmarks-mocks.html. Plan version: 2026-10-03.

The app already has landmarks, so the tool outlines the real header, navigation and main content of every page, not a demo. It lacks a site footer: decision 1 proposes one, so the tool has a contentinfo to show. A sample page still comes in, as a broken and fixed example in Praktyka, because a page that is already correct teaches less than one that is not.

Changes after work started

Picks: 1C (floating button with a panel), 2C (hatched fill, label in the corner), 3A (landmarks as a tree, headings as an outline), 4A with the lesson quiz. Where these conflict with the sections below, these win.

  • One pull request, not four (section 9). Plan, code and content ship together, as in earlier phases.
  • No site footer yet (decision 1). Still open, so on every page the tool reports the missing footer.
  • The button lives in an aside named "Struktura strony". Content outside every landmark is itself a finding, so the tool sits in a landmark of its own, which the scan leaves out. The panel is a native popover: Esc and a click outside close it, and a list row closes it before moving focus, so it never covers the element that takes focus. The button says "włączona" while any outline is on.
  • The lists sit under each frame, not in a shared table (mock 4A). Each frame posts its own scan, so the list goes where the keyboard steps already go.
  • Labels stack. A landmark that starts in the corner of the one around it (breadcrumbs at the top of main) gets its label moved down, so no label hides another.
  • A missing banner or footer is a finding, worded as advice, not a requirement.
  • The lesson comes before "Tabele i struktura" on the developer path, which now has 8 lessons.

  2. Two simulations for examples. punkty-orientacyjne and naglowki join src/content/simulations.ts as a new kind struktura, with content/symulatory/struktura.md. They work in both frames of every example, through the same postMessage the other simulations use, and get a card on /symulatory.
  3. The sample page. A new example punkty-orientacyjne-i-naglowki: a small municipal page, broken (divs, an unnamed second nav, no main, a heading jump from H1 to H4, bold text as a heading) and fixed.
  4. The exercise. A lesson in the developer path with a quiz about that example (mock 4, second part). No new exercise mechanics.

3. The scan

One module, src/content/structure.ts, free of imports from the app like announce.ts, so it runs on the page and inside a demo frame. It takes a root element and returns plain data:

type Landmark = { role: LandmarkRole; name: string; element: Element; children: Landmark[] };
type Heading = { level: 1 | 2 | 3 | 4 | 5 | 6; text: string; element: Element };
type Finding = { kind: FindingKind; element?: Element };
type Structure = { landmarks: Landmark[]; headings: Heading[]; findings: Finding[] };

const landmarkRoles = ["banner", "navigation", "main", "complementary", "contentinfo", "search", "form", "region"] as const;
type LandmarkRole = (typeof landmarkRoles)[number];
  • Roles and names come from dom-accessibility-api (getRole, computeAccessibleName), already a dependency and already bundled into the pattern frames.
  • getRole 0.7 maps header to banner, footer to contentinfo and section to region unconditionally. The scan adds the HTML-AAM rules on top: header and footer inside article, aside, main, nav or section are not landmarks; section and form count only with a name. It also maps the <search> element. These rules get their own unit tests.
  • Hidden content (hidden, display: none, aria-hidden) is skipped, as a screen reader would.
  • Findings, in Polish on the page: no main; more than one main, banner or contentinfo at top level; two landmarks of the same role without distinct names; no H1 or more than one; a skipped heading level; an empty heading; text outside any landmark. Each has a FindingKind literal and a Polish sentence in one typed record, so a new kind without a sentence fails tsc.
  • polishRoles in announce.ts gains banner (baner), main (główny), complementary (uzupełniający), contentinfo (informacje o zawartości) and search (wyszukiwanie), which also fixes their names in the screen reader tables.

4. Outlines and the list

  • The scan writes one attribute per element, data-a11y-landmark="nawigacja: Główna" or data-a11y-heading="H2", and one stylesheet draws them: outline (no layout shift) and a label from content: attr(data-a11y-landmark) / "", empty alt text so screen readers do not read it twice. Turning off removes the attributes. No overlay layer to keep in position on scroll and resize.
  • The label needs position: relative on its host. The scan sets it only on elements whose computed position is static, so the skip link and anything sticky stay as they are.
  • Style: mock section 2 (2A, 2B or 2C). Headings: 2H.
  • The list is part of the tool, not an extra. Landmarks as a tree, headings as an indented outline, findings at the bottom. Each row is a button that moves focus to the element (adding tabindex="-1" where needed), the way D and H jump in a screen reader. Layout: mock section 3.
  • Client-side navigation and content that changes (filters, quiz steps) rescan on a MutationObserver of main, throttled to one scan per animation frame. The list is updated quietly: no live region announces every rescan.

5. The switch and its state

  • Two buttons with aria-pressed, as on the APG page. Mock section 1 decides where.
  • State in a small React context in __root.tsx, kept in sessionStorage so it survives a reload and a client-side navigation, not a new tab. No URL parameter: it would have to travel with every link. On example pages the frames use ?symulacja= as today; the two are independent.
  • The scan module is loaded with a dynamic import() on the first press, so pages pay nothing until someone uses it.

6. The example and the lesson

  • content/praktyka/punkty-orientacyjne-i-naglowki/ with index.md, bad.html, good.html. Effort: 15 minut. Criteria: 1.3.1, 2.4.1, 2.4.6. bad.axe: region, landmark-one-main, heading-order (to confirm against axe while building).

7. Accessibility of the tool itself

  • Never colour alone (1.4.1): every outline has a text label and a line style per role; skipped levels say "pominięty".
  • Outline colours at least 3:1 against both themes' paper (1.4.11); label text on its fill at least 4.5:1. Checked for both themes while building.
  • Forced colours: outlines and labels fall back to CanvasText and Canvas, line styles keep roles apart.
  • Labels have pointer-events: none and sit inside the outline, so they never take a click. A label must not cover the focused element (2.4.11): the label sits at the edge of its landmark, and the focused element gets scroll-margin for its height.
  • Buttons in the switches and the list at least 44×44 (2.5.5). No animation, so nothing for prefers-reduced-motion to turn off.
  • The page passes axe with the tool on (it adds no landmarks of its own; the side panel from 3A is an aside with a name, which the scan leaves out of its own list).

8. Tests

  • Vitest on structure.ts with jsdom fixtures: header scoping, unnamed section and form, <search>, hidden content, each finding kind. One test per rule, no snapshot.
  • Playwright: turn on both switches on / and on a criterion page, check the list rows and that axe passes; press a row and check focus. The new example goes through the existing example tests (axe on the fixed fragment, bad.axe rules).
  • The content tests already fail on a role without a Polish name; the new roles go through them.

10. Decisions

  1. Add a site footer? Recommendation: yes, short: the draft note ("Treści są szkicami do sprawdzenia"), the repository link and a link to /symulatory. It gives the tool a contentinfo to show, and a site that teaches landmarks should have the full set. Footer copy goes to chat as wording variants.
  2. Where the switches live: 1A, 1B or 1C. Recommendation: 1B. The header stays as it is for everyone else, and the bar makes it obvious the page is in a special mode.
  3. Regions on our own pages: recommendation: ship the tool first and let it show the count, then in a separate PR drop aria-labelledby from sections nobody needs to jump to, keeping regions only where the TOC does not already help.
  4. Outline style: 2A, 2B or 2C. Recommendation: 2A, closest to the brief and readable without the list.
  5. The list: 3A or 3B. Recommendation: 3A on wide screens, falling back to 3B under the content below 900 px.
  6. Exercise: 4A alone, or 4A with the lesson quiz. Recommendation: with the quiz.

11. Out of scope

  • Keyboard shortcuts that imitate screen reader landmark navigation (D, H). They would clash with the browser and with real screen readers.
  • Outlines for other roles (lists, tables, forms without names). The tool shows what a screen reader lets you jump between, nothing else.
  • Editing the structure in the frame.
